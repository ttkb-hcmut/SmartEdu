### 1. Microsoft GraphRAG
**Category:** framework · **Maturity:** production (open-sourced, integrated into Azure/Microsoft Discovery) · **Source:** *From Local to Global: A Graph RAG Approach to Query-Focused Summarization* (arXiv:2404.16130, Apr 2024); repo `microsoft/graphrag`.

**Methodology.** GraphRAG runs a heavyweight **offline indexing pipeline**: it chunks the corpus, then uses an LLM to extract typed entities and relationships from each chunk (with "gleanings" — repeated extraction passes to raise recall), producing an entity-relationship graph whose edges carry LLM-written descriptions. It then runs **Leiden hierarchical community detection** to partition the graph into nested communities at multiple resolutions, and pre-generates an LLM **community report** (summary) for every community at every level. At query time it offers two complementary modes. **Global search** answers sense-making / "what are the themes" questions with a **map-reduce over community summaries**: each community summary independently produces a partial answer with a self-rated helpfulness score (map), and the top-scoring partials are reduced into one response. **Local search** answers entity-centric questions by finding the query's nearest entities (vector similarity on entity descriptions), then fanning out to their neighbors, connected communities, and source text chunks, ranking and packing that neighborhood into the context window. The QA answer therefore comes either from aggregated community reports (global) or an assembled entity neighborhood (local). **Strengths:** best-in-class on corpus-wide "global" questions that flat RAG cannot answer; explainable provenance. **Limitations:** indexing is extremely LLM-expensive (many calls per chunk plus per-community summaries); rigid two-mode split; costly to keep fresh. SmartEdu's `CommunityNode`/`TopicNode`/`Cluster` structure is essentially a lighter-weight, course-scoped version of this hierarchy.

### 2. LazyGraphRAG
**Category:** framework / retrieval strategy · **Maturity:** production (Microsoft Research; integrated into Azure Local & Microsoft Discovery, 2025) · **Source:** Microsoft Research blog, *LazyGraphRAG sets a new standard for quality and cost* (Nov 2024).

**Methodology.** LazyGraphRAG is a direct response to GraphRAG's indexing cost. It **defers all LLM summarization to query time** ("lazy"). Offline it does only cheap, LLM-free work: extract noun-phrase concepts, build a co-occurrence graph, and run community detection — no per-entity or per-community LLM summaries at all, cutting indexing cost to ~0.1% of full GraphRAG. At query time it uses a **best-first + breadth-first iterative-deepening** hybrid: it vector-ranks the most relevant communities to the query, then within a budget it drills down, using an LLM only on the specific text chunks it actually needs to relevance-test and extract claims from, refining the sub-corpus until it can compose an answer. This "single flexible query mechanism" reportedly matches full GraphRAG quality across the local↔global spectrum at ~700× lower global-query cost. **Strengths:** near-zero indexing cost, excellent for streaming/one-off corpora, tunable cost/quality budget. **Limitations:** shifts cost to query latency; less pre-computed structure to reuse across queries. Highly relevant as a design philosophy for SmartEdu if per-course indexing budget is a concern.

### 3. LightRAG
**Category:** framework · **Maturity:** mature OSS (very widely adopted) · **Source:** *LightRAG: Simple and Fast Retrieval-Augmented Generation* (arXiv:2410.05779, Oct 2024).

**Methodology.** LightRAG builds a graph index by LLM-extracting entities and relations (each with a keyword/description profile) and deduplicating them, storing nodes/edges alongside their embeddings in a vector store — deliberately **no expensive community-summary layer**. Its signature is **dual-level retrieval** driven by the LLM extracting two keyword sets from the query: **low-level keywords** (specific entities/attributes) retrieve fine-grained nodes and their local relations for precise questions, while **high-level keywords** (abstract themes) retrieve *relations/edges* that capture broad topics. Both retrievals gather the relevant entities, relations, and their source chunks, which are merged and de-duplicated into a single context for one-shot generation — there is no iterative graph walk. A second contribution is an **incremental update algorithm**: new documents are extracted and merged into the existing graph/vector store without reprocessing the corpus, so the index stays current cheaply. **Strengths:** ~60% lower indexing token cost and roughly halved query latency vs GraphRAG at comparable multi-hop quality; genuinely incremental; huge community adoption. **Limitations:** no reflective/agentic loop (single pass); dual-level keyword extraction quality bounds retrieval; can still retrieve redundant neighborhoods (the exact problem PathRAG targets).

### 4. KAG — Knowledge Augmented Generation (OpenSPG)
**Category:** framework · **Maturity:** production (Ant Group + Zhejiang Univ.; deployed on Ant e-Gov and e-Health QA) · **Source:** *KAG: Boosting LLMs in Professional Domains via Knowledge Augmented Generation* (arXiv:2409.13731, Sep 2024); engine `OpenSPG/openspg`, framework `OpenSPG/KAG`.

**Methodology.** KAG targets *professional/rigorous* domains where fluent-but-wrong answers are unacceptable, and fuses symbolic KG reasoning with LLM generation over the **SPG (Semantic-enhanced Programmable Graph)** engine. It has four pillars: (1) an **LLM-friendly knowledge representation (LLMFriSPG)** that stores both schema-constrained facts and looser text, tolerating mixed structure; (2) a **mutual index** between the KG and the original text chunks so retrieval can move between symbolic nodes and source passages; (3) a **logical-form-guided hybrid reasoning solver** — the LLM decomposes a complex question into a program of logical-form operators (retrieval, math, deduction), which are executed step-by-step against the graph, mixing symbolic execution with LLM inference; and (4) a **knowledge-alignment** step using semantic reasoning to link and disambiguate concepts (hypernym/synonym normalization) so extraction noise doesn't fragment the graph. The answer is assembled from the executed logical-form plan grounded in retrieved facts. Reported ~19.6% (HotpotQA) and ~33.5% (2Wiki) relative F1 gains over prior methods. **Strengths:** strongest fit where faithfulness and multi-step logical rigor matter (compliance, health, education-with-guarantees); explicit knowledge alignment mirrors SmartEdu's Wikidata resolution. **Limitations:** heavy stack (OpenSPG engine, schema modeling); steeper setup; logical-form solver adds latency.

### 5. fast-graphrag / nano-graphrag (Circlemind)
**Category:** framework · **Maturity:** mature OSS (MIT) · **Source:** `circlemind-ai/fast-graphrag`; lineage from `gusye1234/nano-graphrag`.

**Methodology.** nano-graphrag is a ~1k-line reimplementation of GraphRAG's core (extract → graph → community → local/global query) that strips the map-reduce global search down to selecting only the **top-k communities** instead of scoring all of them, making it far cheaper and hackable; it became the substrate for LightRAG, MedGraphRAG, and others. **fast-graphrag** then replaces GraphRAG's community-summary machinery with **Personalized PageRank exploration**: it builds an entity graph, and at query time seeds PageRank from the query-relevant entities/chunks and lets the random-walk stationary distribution rank which nodes and chunks are most relevant to pull into context — the same HippoRAG-style intuition, packaged as a drop-in retrieval library that "gives you advanced RAG without building agentic workflows." It also supports incremental updates and typed schemas. **Strengths:** minimal, readable, cheap, MIT-licensed, easy to fork; PageRank retrieval is strong on multi-hop; good reference implementation for a self-hosted stack like SmartEdu. **Limitations:** thinner tooling/observability than the big frameworks; non-agentic by default (retrieval library, not a reasoning loop).

### 6. Neo4j GraphRAG + LlamaIndex PropertyGraphIndex (production stack)
**Category:** framework (production integration layer) · **Maturity:** production · **Source:** Neo4j GenAI docs / `neo4j-graphrag-python`; LlamaIndex `PropertyGraphIndex` docs.

**Methodology.** This is the mainstream *production* path rather than a single algorithm. **LlamaIndex `PropertyGraphIndex`** constructs a property graph by running a configurable chain of `kg_extractors` over each chunk (schema-guided or free-form LLM extraction, or implicit path extraction), attaching entities/relations as node metadata and persisting to a graph store (commonly Neo4j). Retrieval composes pluggable **sub-retrievers**: `VectorContextRetriever` (embedding search over nodes) and `TextToCypherRetriever` (LLM writes a Cypher query executed live against Neo4j), whose results merge into the LLM context. In an **agentic** setup these retrievers are exposed as *tools* to a `FunctionAgent`, so the agent chooses between semantic search, Cypher, and neighborhood expansion per step — and Neo4j's native vector index means one store serves both graph traversal and vector search. **Strengths:** durable storage, provenance, mature ops, hybrid vector+Cypher, MCP/tool integration — the closest analog to SmartEdu's own "graph tools + SemanticSearch exposed to an agent" design. **Limitations:** you assemble the intelligence yourself (fusion, reflection, gap-detection are not provided); text-to-Cypher reliability varies with schema complexity.

### 7. HippoRAG / HippoRAG 2 (Personalized PageRank memory)
**Category:** retrieval technique · **Maturity:** research→OSS (HippoRAG NeurIPS'24; HippoRAG 2 Feb 2025) · **Source:** arXiv:2405.14831; *From RAG to Memory* arXiv:2502.14802; `OSU-NLP-Group/HippoRAG`.

**Methodology.** HippoRAG is inspired by the hippocampal indexing theory of human memory. **Offline:** an LLM does OpenIE over passages to extract (subject, predicate, object) triples, which are assembled into an **open knowledge graph** of phrase/entity nodes; an encoder adds **synonym edges** between semantically similar phrase nodes. **Online:** the query's named entities are matched to graph nodes and used as the **seed (personalization) vector for Personalized PageRank (PPR)**; a single PPR run diffuses probability across the KG so that multi-hop-relevant nodes light up, and passages are ranked by the PPR mass of the phrases they contain — achieving multi-hop retrieval in *one* graph computation instead of iterative LLM-driven hops. **HippoRAG 2** upgrades this to a **dual-node graph combining dense passage nodes with the phrase/triple nodes**, integrates dense embeddings more deeply into the PPR seeding, and adds an **LLM "recognition-memory" triple-filtering** step that prunes spurious extracted triples before graph reasoning — unifying dense and sparse retrieval. It reports ~+7 F1 on associative/multi-hop QA over strong embedding retrievers while keeping offline indexing cheaper than GraphRAG. **Strengths:** single-shot multi-hop via PPR (fast, no per-hop LLM calls), continual/incremental knowledge integration, strong sense-making. **Limitations:** quality bounded by OpenIE/triple extraction; PPR hyper-parameters need tuning; graph must be maintained.

### 8. G-Retriever
**Category:** retrieval technique · **Maturity:** research (NeurIPS'24) · **Source:** *G-Retriever: RAG for Textual Graph Understanding and QA* (arXiv:2402.07630).

**Methodology.** G-Retriever is the first general RAG method for **textual graphs** (nodes/edges carry text), designed so a chat LLM can answer questions and resist hallucination on graphs bigger than its context window. **Indexing:** node and edge text are embedded with a pre-trained LM into a nearest-neighbor index. **Retrieval:** k-NN pulls the query-relevant nodes and edges (each assigned a "prize" from its query similarity). **Subgraph construction:** it solves a **Prize-Collecting Steiner Tree (PCST)** optimization — find a *connected* subgraph maximizing collected node/edge prizes minus edge costs — yielding a compact, connected, explainable subgraph rather than a bag of nodes. **Generation:** a **Graph Attention Network encodes the subgraph into a soft graph token**, a projection layer aligns it to the LLM embedding space, and the subgraph is *also* verbalized as text; the LLM is fine-tuned via **soft prompting** to answer from both the graph token and the textualized subgraph. **Strengths:** returns an interpretable connected subgraph; scales beyond context limits; the GNN+LLM fusion is efficient (train only the projector/soft prompt). **Limitations:** needs training (GNN + soft prompt); PCST assumes a meaningfully connected textual graph; less "plug-and-play" than prompt-only methods.

### 9. PathRAG
**Category:** retrieval technique · **Maturity:** research OSS · **Source:** *PathRAG: Pruning Graph-based RAG with Relational Paths* (arXiv:2502.14902, Feb 2025).

**Methodology.** PathRAG's thesis is that the failure mode of GraphRAG/LightRAG is **redundancy, not insufficiency** — GraphRAG dumps whole communities, LightRAG dumps all immediate neighbors, both flooding the prompt with noise. PathRAG instead retrieves **key relational *paths* between query-related nodes.** After identifying query-relevant nodes (via keyword/embedding matching on the indexing graph), it applies **flow-based pruning**: it models relevance as a resource that flows outward from source nodes and **decays with distance** (a decay/penalty rate per hop), so long, weakly-connected paths are down-weighted and only high-"flow" paths between the relevant nodes survive. Surviving paths are scored for reliability and then, crucially, **ordered in the prompt by ascending reliability** (best path last / nearest the question) — an empirically motivated **path-based prompting** ordering that improves LLM coherence. The answer is generated from these concise, logically-connected paths. It reports consistent wins over GraphRAG/LightRAG across six datasets and five evaluation dimensions with far fewer tokens. **Strengths:** cuts token cost and noise, produces *reasoning-shaped* (path) context, directly attacks redundancy. **Limitations:** paths only help when the graph encodes meaningful multi-hop relations; decay/flow parameters need tuning; still single-pass (not agentic on its own).

### 10. RAPTOR
**Category:** retrieval technique (tree, not strictly graph) · **Maturity:** research (ICLR'24), widely adopted in practice · **Source:** *RAPTOR: Recursive Abstractive Processing for Tree-Organized Retrieval* (arXiv:2401.18059; Sarthi et al., Stanford).

**Methodology.** RAPTOR builds a **multi-level summary tree bottom-up**: leaf nodes are text chunks; it embeds them, **soft-clusters** similar chunks (Gaussian-mixture over reduced embeddings so a chunk can join multiple clusters), and has an LLM **summarize each cluster** into a parent node; it recurses on the parent summaries until a root, giving progressively more abstract nodes up the tree. At query time it retrieves either by **collapsing the whole tree into one pool** and doing top-k over all nodes at all abstraction levels (the mode that works best), or by tree traversal — so a single query can pull both a fine-grained leaf detail and a high-level thematic summary. The answer is generated from that mixed-abstraction context. On multi-step-reasoning QA (e.g. QuALITY, QASPER) RAPTOR + GPT-4 set SOTA at release. **Strengths:** cheap (only summarization, no entity graph), captures document-level context that flat chunking misses, trivially bolted onto existing vector RAG. **Limitations:** hierarchy is *thematic* not *relational* (no cross-entity edges), so it's weaker on entity-linking multi-hop than true GraphRAG; summaries can drift.

### 11. Think-on-Graph — ToG → ToG-2 → ToG-3
**Category:** agentic pattern · **Maturity:** research (ToG ICLR'24; ToG-2 ICLR'25; ToG-3 Sep 2025) · **Source:** arXiv:2307.07697 · arXiv:2407.10805 · arXiv:2509.21710.

**Methodology.** ToG treats the **LLM as an agent that beam-searches over a knowledge graph.** Starting from the question's entities, each iteration: (1) **explore** — the LLM scores and prunes candidate relations then candidate neighbor entities to keep the top-N reasoning paths (beam width N); (2) **reason** — the LLM judges whether the current paths suffice to answer; if yes it answers, else it takes another hop. Because reasoning rides on explicit KG paths, answers are **traceable and correctable**, and it's training-free/plug-and-play. **ToG-2** makes it **hybrid and tightly-coupled**: it alternates **graph retrieval and document (context) retrieval** — the KG links documents via entities to guide deep context retrieval, while the retrieved documents serve as entity context to sharpen the next graph hop — iterating until the clues are deep enough to answer. **ToG-3** (2025) generalizes to **heterogeneous graphs with a multi-agent, dual-evolving context** that constructs/refines graph structure on the fly during reasoning, improving efficiency and adaptivity. The answer always comes from the LLM reasoning over the iteratively-assembled path+context evidence. **Strengths:** genuinely agentic multi-hop, interpretable paths, hybrid structured+unstructured (ToG-2), no training. **Limitations:** many sequential LLM calls per query (latency/cost); beam search can miss paths; needs a good entity-linking entry point.

### 12. GraphReader
**Category:** agentic pattern · **Maturity:** research (EMNLP'24 Findings; Alibaba et al.) · **Source:** *GraphReader: Building Graph-based Agent to Enhance Long-Context Abilities of LLMs* (arXiv:2406.14550).

**Methodology.** GraphReader tackles **long-context** by turning a long document into a graph the agent *explores* rather than reads whole. It segments the text, and for each segment an LLM extracts atomic facts and key elements, building a graph whose **nodes are key concepts holding their associated atomic facts** and whose edges link co-occurring/related concepts. At query time the agent first **plans** (decomposes the question into a rational sub-goal plan and maintains a notebook), then invokes a fixed set of **predefined functions** — read a node's atomic facts, read a node's chunk, look up neighbors — to do **coarse-to-fine exploration**: it starts from promising nodes, records new insights to the notebook, reflects on whether it has enough, and hops onward, terminating when the notebook supports an answer. The answer is composed from the accumulated notebook. Notably a **4k-context model using GraphReader beats GPT-4-128k** from 16k–256k inputs. **Strengths:** strong on very long single-document/multi-hop QA with a small model; explicit plan+notebook+reflect loop is a clean agentic template. **Limitations:** graph is built per-document/corpus with LLM extraction cost; exploration is many LLM steps; designed around reading rather than a persistent curated KG.

### 13. Graph-CoT (Graph Chain-of-Thought)
**Category:** agentic pattern · **Maturity:** research (ACL'24 Findings; Jin et al.) · **Source:** arXiv:2404.07103; `PeterGriffinJin/Graph-CoT`; benchmark **GRBench**.

**Methodology.** Graph-CoT argues that feeding a whole subgraph to the LLM is wasteful and error-prone, so it makes the LLM **reason on the graph iteratively, one hop per step.** Each iteration has three sub-steps: (1) **LLM reasoning** — the model states what information it still needs; (2) **LLM–graph interaction** — it emits a call to a small API of graph functions (retrieve a node, fetch neighbors, fetch a node's feature/degree, etc.); (3) **graph execution** — the function runs and returns the result, which feeds the next reasoning step. The chain of hops *is* the chain-of-thought, and the final step emits the answer grounded in the traversed nodes. The authors ship **GRBench** (1,740 questions over 10 real domain graphs across academic, e-commerce, literature, healthcare, legal) to evaluate this, and Graph-CoT beats non-interactive baselines across three LLM backbones. **Strengths:** minimal, general "reason→call graph function→observe" loop that maps directly onto tool-calling agents; interpretable; works over any graph exposed as a function API. **Limitations:** step-wise LLM calls add latency; performance depends on the graph-function API design; no built-in fusion with vector/text retrieval.

### 14. Self-RAG & Corrective RAG (CRAG)
**Category:** agentic pattern (reflective / corrective control) · **Maturity:** research→widely adopted (LangGraph reference implementations) · **Source:** *Self-RAG* (arXiv:2310.11511, ICLR'24) · *CRAG* (arXiv:2401.15884).

**Methodology.** These are not graph methods but the dominant **agentic control loops** layered on top of retrieval — highly relevant because SmartEdu's `Deep_Decision`/`rag_deep` is exactly this genre. **Self-RAG** trains one model to emit special **reflection tokens** that make retrieval and generation *adaptive and self-critiqued*: a `Retrieve` token decides on-demand whether retrieval is even needed for the next span; `IsRel`/`IsSup`/`IsUse` critique tokens then score whether retrieved passages are relevant, whether the generated claim is *supported* by them, and whether the answer is useful — the model can retrieve, grade, and re-generate, choosing the best-supported continuation. **CRAG** is a lighter, model-agnostic wrapper: a lightweight **retrieval evaluator** scores each retrieved chunk as *Correct / Ambiguous / Incorrect*; "Correct" triggers a **knowledge-refinement** decompose-then-recompose step to strip noise, while "Incorrect/Ambiguous" **triggers a fallback** (e.g. web search) to replace weak evidence before generation. Both put a **grade-and-correct gate between retrieval and answering.** **Strengths:** measurable faithfulness gains, decoupled from retrieval backend, easy to express as LangGraph nodes/edges. **Limitations:** Self-RAG needs fine-tuning to emit reflection tokens (or prompt-emulation); extra LLM grading calls; corrective fallbacks add latency.

### 15. GraphRAG-Bench + DIGIMON (unified evaluation & analysis)
**Category:** eval harness · **Maturity:** research (GraphRAG-Bench ICLR'26; DIGIMON/unified-framework 2025) · **Source:** *GraphRAG-Bench* (arXiv:2506.02404) · *In-Depth Analysis of Graph-based RAG in a Unified Framework* (arXiv:2503.04338, "DIGIMON").

**Methodology.** As GraphRAG methods multiplied, two efforts standardized comparison. **DIGIMON / the unified-framework paper** decomposes graph-RAG systems into interchangeable **operators** (graph construction type, node/edge/community retrieval operators, ranking, generation) so that GraphRAG, LightRAG, HippoRAG, etc. can be re-expressed and A/B'd within one modular harness — its finding is that *no single design wins everywhere* and the right operators depend on query type and corpus. **GraphRAG-Bench** is a **domain-specific reasoning benchmark** (16 disciplines, 20 core textbooks) that evaluates the *whole* pipeline — construction, retrieval, and generation — and, critically, scores **reasoning-process coherence, not just final-answer correctness**, across multiple question formats (multiple-choice, multi-select, true/false, open-ended, fill-in-the-blank). Its companion analysis, *When to use Graphs in RAG* (arXiv:2506.05690), characterizes exactly which query types graphs help on. **Strengths:** apples-to-apples comparison; textbook/education-shaped data that is unusually on-target for SmartEdu; process-level (not just answer) scoring. **Limitations:** benchmarks lag the newest methods; harness setup effort; DIGIMON evaluates retrieval mechanics more than end-to-end reasoning.

### 16. RAGAS / ARES (component-level RAG evaluation)
**Category:** eval harness · **Maturity:** mature OSS · **Source:** *RAGAS* (arXiv:2309.15217) · *ARES* (arXiv:2311.09476).

**Methodology.** Both give **reference-light, LLM-graded** metrics decomposing a RAG system into retrieval and generation quality. **RAGAS** decomposes each generated answer into **atomic factual statements** and, using an LLM judge, computes **Faithfulness** (fraction of statements entailed by the retrieved context — a hallucination detector), **Answer Relevance** (does the answer address the question), and **Context Relevance/Precision/Recall** (did retrieval fetch the right context); it needs no gold answers, enabling continuous/CI evaluation. **ARES** instead **fine-tunes lightweight LM judges** on *synthetic* query-passage-answer data to score context relevance, answer faithfulness, and answer relevance, and uses **prediction-powered inference (PPI)** with a small human-labeled set to statistically de-bias the judges' predictions and give confidence intervals — reporting large accuracy gains over RAGAS on context relevance. The answer under test comes from the RAG system; these harnesses only *grade* it. **Strengths:** cheap, automatable, component-diagnostic (tells you if retrieval vs generation is the weak link), CI-friendly. **Limitations:** LLM-judge bias/variance (ARES's PPI mitigates but needs labels); metrics are proxies; graph-specific reasoning quality needs the GraphRAG-Bench-style harnesses above.

## 2. Top 3 for SmartEdu

SmartEdu's differentiators are: a **course-scoped typed KG** (`ConceptNode`/`RhetoricalNode`/`TopicNode`/`CommunityNode`/`Cluster`) built by `KG_Handler`; **hybrid graph + vector retrieval exposed as agent tools**; and an **agentic knowledge-gap loop** (`Deep_Decision → rag_deep`) that proposes **prerequisite "bridge" concepts** anchored to the student's `current_pos`. The picks below target its two real gaps — **(A) no principled query-time fusion/multi-hop retrieval** (the assumed "RRF merge" does not exist in code) and **(B) bridge proposals are concept *lists*, not scored prerequisite *paths***.

### Pick 1 — HippoRAG 2 (Personalized PageRank fusion over the concept graph)
**Why it fits.** SmartEdu already has exactly the two ingredients HippoRAG 2 needs and currently under-uses: a phrase/concept graph (Neo4j `ConceptNode`s with `RhetoricalNode` sub-facts and typed edges) *and* a dense passage store (Milvus, via `SemanticSearch`). Today these are two **separate tools** the LLM picks between; there is no fusion (the briefing's "RRF merge" is absent from `capstone/`). HippoRAG 2 is precisely a principled fusion: **seed Personalized PageRank from the query's matched concept nodes (and dense-retrieved passages), run one PPR pass over the existing KG, and rank concepts/passages by diffused mass** — giving single-shot, multi-hop, associative retrieval instead of ad-hoc tool selection. Its dual passage+phrase node design maps one-to-one onto SmartEdu's Concept↔Milvus-chunk pairing, and its LLM triple-filtering mirrors the `semantic_merge` dedup you already do at construction time.

**Components it touches.** `SemanticSearch` (Milvus) → PPR seed/personalization vector; `EntityFinder`/`EdgeExplorer` (Neo4j edges) → the graph PPR runs over; **a new `HybridPPRRetriever`** that replaces the missing RRF step; optionally the `Cluster`/`CommunityNode` weights as PPR priors.

**Effort:** Medium. PPR itself is cheap (Neo4j GDS has `gds.pageRank` with a `sourceNodes` personalization arg, or `networkx.pagerank(personalization=…)` on an in-memory ego-graph). The work is entity-linking the query to seed nodes and tuning damping/seed weights.

**Next steps.** (1) Add a `HybridPPRRetriever` tool: match query entities via `EntityFinder` + top-k Milvus hits, build the seed vector, run personalized PageRank (Neo4j GDS or `networkx`), return top concepts+chunks by score. (2) Wire it as the fusion step feeding `RAG_Core` instead of leaving fusion to LLM tool-choice. (3) A/B against current tool-calling on a held-out set of course questions using RAGAS faithfulness + context-recall (Pick-adjacent, see below).

### Pick 2 — PathRAG (flow-based relational-path pruning for bridge concepts)
**Why it fits.** The `rag_deep` bridge mechanism is *fundamentally a path problem*: given the student's `current_pos` and a target concept, find the **prerequisite chain** to splice into `new_current`/`new_upcoming`. Right now `RAGDeep.bridge_concepts` is an LLM-produced **list of concepts** with no guarantee they form a coherent, non-redundant learning path. PathRAG's **flow-based pruning** — relevance flows from source nodes and decays per hop, keeping only high-flow paths between the two endpoints — is exactly the algorithm for selecting a *minimal, ordered, prerequisite path* from `current_pos` to the target over your concept graph. Its **path-based prompting** (order paths by reliability, best nearest the question) also gives a principled ordering for `new_upcoming`. This upgrades bridge proposals from "concepts the model guessed" to "the pruned prerequisite path the graph supports," while cutting token noise.

**Components it touches.** `OptimalPath`/`CourseTree` tools (`tools/neo/course_tree.py`, `explore.py`) → path enumeration; `rag_deep` in `retrieve.py:202-290` → replace/augment `bridge_concepts` generation with pruned paths; `pending_proposal` (`type="bridge"`, `new_current`/`new_upcoming`) → populate from the ordered path; `tree_order.py`/`roadmap.py` → splice point.

**Effort:** Medium. You already have graph traversal tools; PathRAG adds a flow/decay scoring + pruning pass and a prompt-ordering rule. No training required.

**Next steps.** (1) Implement flow-based pruning over paths between `current_pos` node and the target concept (resource init at source, per-hop decay α, prune below threshold). (2) Feed the top pruned paths (ascending reliability) into the `rag_deep` prompt so `bridge_concepts` becomes a *validated ordered path*. (3) Validate that spliced bridges respect the course topo-order already computed in `course_tree.py`.

### Pick 3 — Think-on-Graph 2.0 (agentic hybrid graph+context loop for the deep branch)
**Why it fits.** SmartEdu's `Deep_Decision → rag_deep` is already a nascent agentic branch, but `rag_deep` is a **single structured-output call**, not an iterative loop — so on genuinely multi-hop gap questions it gets one shot at assembling evidence. ToG-2 is the mature template for what that branch *wants to be*: an **iterative loop alternating graph retrieval and document/context retrieval** — use the concept graph (`EntityFinder`/`EdgeExplorer`/`OptimalPath`) to find the next relevant concepts, use `SemanticSearch` to pull the `RhetoricalNode`/Milvus text that contextualizes them, decide if the gap is characterized, and hop again if not. This directly strengthens **bridge detection**: instead of guessing prerequisites in one pass, the agent *walks* from `current_pos` toward the query concept, discovering the true missing links. It also composes cleanly with Picks 1–2 (PPR for seeding a hop, PathRAG for scoring the resulting paths) and with the existing `RecallToolResults`/`RecallThoughts` memory for cross-turn continuity.

**Components it touches.** `rag_deep` node → convert from single call to a bounded ToG-2 iterate loop (add a LangGraph sub-cycle or an internal while-loop with a step budget); graph tools + `SemanticSearch` as the alternating retrievers; `Deep_Decision` → natural place for the ToG-style "is the evidence deep enough?" stop condition; `AgentTracer`/Langfuse → trace each hop.

**Effort:** Medium-High. Requires restructuring `rag_deep` into an iterative controller with a hop budget and a stop criterion, plus guarding latency/cost (cap N hops). Reuse `Deep_Decision`'s classifier pattern for the per-hop "sufficient?" check.

**Next steps.** (1) Prototype a 2–3 hop bounded loop in `rag_deep`: graph-hop (pick next concepts) → context-fetch (`SemanticSearch`/`RhetoricalRetriever`) → sufficiency check → answer or hop. (2) Cap hops and record each hop in `AgentTracer` for cost/quality analysis. (3) Layer Pick 1 (PPR to choose promising next nodes) and Pick 2 (PathRAG to score/prune the discovered bridge path) inside the loop.

> **Honorable mentions for SmartEdu.** *Self-RAG/CRAG* — add an `IsSup`-style faithfulness gate before returning teaching content (cheap, high-value, fits the existing node/edge control flow). *GraphRAG-Bench + RAGAS* — adopt as the evaluation harness: GraphRAG-Bench is *textbook-shaped* (16 disciplines) and scores reasoning coherence, and RAGAS gives CI-friendly faithfulness/context-recall to measure whether Picks 1–3 actually help. *Microsoft GraphRAG global search* — SmartEdu's `CommunityNode`/`Cluster` layer already mirrors GraphRAG communities, so a map-reduce "summarize this whole course/topic" mode is a low-friction add for high-level student questions.
